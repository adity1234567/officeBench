Where the runs come from, and how their failures are named

Four figures for the paper. The first is the general pipeline, step by step; the second walks one real subtask through it; the last two are the apparatus and the coding instrument in detail. Every number and every quoted string is from the runs themselves, as of 2026-10-04.

Using these in the paper

The drawings are vector files, not screenshots: analysis/figures/fig0_teaser.svg, fig1_study_design.svg and fig2_failure_coding.svg. All three use currentColor for every line and label, so they print black on white without edits; the amber elements mark the path the paper argues about. The teaser is static and complete on its own — the interaction above is page JavaScript bound to ids inside it, so the file drops straight into LaTeX. Rebuild with make_fig0_teaser.py, then build_figures_page.py.

Where the numbers come from

The worked example is subtask 1-2/0: task and checks from tasks/1-2/subtasks/0.json, busy blocks from the two .ics files in tasks/1-2/testbed/calendar/, the four steps and both answers from tasks/1-2/outputs/0/gemma4_31b_{think,bn}/env_history.json. Pass counts and root-cause totals: analysis/failure_codes_all_runs.json (557 coded failures: 149 gemma English, 173 gemma Bangla, 214 gpt-oss English, 21 gpt-oss Bangla). Agreement: analysis/agreement.py over labels_A.csv and labels_B.csv, κ = 0.78 on the primary code and 0.64 on the benchmark-versus-agent split, n = 16. Coding rules: analysis/codebook.md. The gpt-oss Bangla cell is 51 of 300 subtasks and is still running.
